# B4-1 요구사항 수행 내역서

컴퓨터가 알아서 자기 상태를 점검하게 만들기

평가 기준은 BX-X의 [미션 원문](https://github.com/parkhojeong/BX-X/blob/53de3357589be202f82d9314e7cd97c91b71ee5c/B4-1.md)과 [체크리스트](https://github.com/parkhojeong/BX-X/blob/53de3357589be202f82d9314e7cd97c91b71ee5c/checklists/B4-1-checklist.md)다. 아래 주석의 번호는 체크리스트의 항목 번호와 그 안의 질문 순서다. 예를 들어 `1-4`는 항목 1의 네 번째 질문이다. 설명·장애 대응 질문은 [단계별 문서](../README.md#작은-과제로-나눈-순서)에 정리했다.

## 1. 수행 환경

```text
$ . /etc/os-release; echo "OS: $PRETTY_NAME"; echo "ARCH: $(uname -m)"; echo "TIMEZONE: $(cat /etc/timezone)"; date "+CHECKED_AT: %F %T %Z"
OS: Ubuntu 22.04.5 LTS
ARCH: aarch64
TIMEZONE: Asia/Seoul
CHECKED_AT: 2026-11-19 03:14:06 KST
```

- 실습 환경은 macOS의 OrbStack에서 실행한 `ubuntu:22.04` 컨테이너(`b4-1`)다.
- 컨테이너는 자체 네트워크 네임스페이스를 가지므로 방화벽 규칙이 호스트와 다른 환경에 영향을 주지 않는다.
- 제공 앱은 CPU 구조에 맞는 `agent-app-linux-arm64`를 사용했다.

## 3. 수행 내역(설정/명령어 기록)

### 3.1 컨테이너 생성

방화벽을 사용하기 위해 `NET_ADMIN`, `NET_RAW` 권한만 추가했고 `--privileged`는 사용하지 않았다.

```sh
docker --context orbstack run -d --name b4-1 --hostname b4-1 \
  --cap-add NET_ADMIN --cap-add NET_RAW \
  -p 127.0.0.1:20022:20022 -p 127.0.0.1:15034:15034 \
  ubuntu:22.04 bash -c 'service ssh start 2>/dev/null; service cron start 2>/dev/null; exec sleep infinity'

# 이후 설정 명령은 컨테이너의 root 셸에서 실행한다.
docker --context orbstack exec -it b4-1 bash
apt-get update
apt-get install -y openssh-server acl cron tzdata ufw iptables iproute2 procps sudo
ln -sf /usr/share/zoneinfo/Asia/Seoul /etc/localtime
echo Asia/Seoul > /etc/timezone
service cron start
```

### 3.2 SSH

```sh
sed -i -E 's/^#?[[:space:]]*Port[[:space:]].*/Port 20022/' /etc/ssh/sshd_config
sed -i -E 's/^#?[[:space:]]*PermitRootLogin[[:space:]].*/PermitRootLogin no/' /etc/ssh/sshd_config
install -d -m 755 /run/sshd
sshd -t
service ssh restart
```

### 3.3 방화벽(UFW)

```sh
ufw default deny incoming
ufw default allow outgoing
ufw allow 20022/tcp
ufw allow 15034/tcp
ufw --force enable
```

### 3.4 계정, 그룹, 디렉토리, 권한

```sh
groupadd agent-common
groupadd agent-core
useradd -m -s /bin/bash agent-admin
useradd -m -s /bin/bash agent-dev
useradd -m -s /bin/bash agent-test
usermod -aG agent-common,agent-core agent-admin
usermod -aG agent-common,agent-core agent-dev
usermod -aG agent-common agent-test

AGENT_HOME=/home/agent-admin/agent-app
mkdir -p "$AGENT_HOME"/{upload_files,api_keys,bin} /var/log/agent-app

# 홈은 프로젝트 구성원에게 통과 권한만 준다.
chmod 750 /home/agent-admin
setfacl -m g:agent-common:--x /home/agent-admin
chown agent-admin:agent-common "$AGENT_HOME"
chmod 750 "$AGENT_HOME"

# upload_files: agent-common R/W
chown agent-admin:agent-common "$AGENT_HOME/upload_files"
chmod 2770 "$AGENT_HOME/upload_files"
setfacl -m g:agent-common:rwx,o::--- "$AGENT_HOME/upload_files"
setfacl -d -m g:agent-common:rwx,o::--- "$AGENT_HOME/upload_files"

# api_keys, 로그 디렉토리: agent-core만 R/W
for d in "$AGENT_HOME/api_keys" /var/log/agent-app; do
  chown agent-admin:agent-core "$d"
  chmod 2770 "$d"
  setfacl -m g:agent-core:rwx,o::--- "$d"
  setfacl -d -m g:agent-core:rwx,o::--- "$d"
done

# bin: agent-dev가 작성하고 agent-core가 실행한다.
chown agent-dev:agent-core "$AGENT_HOME/bin"
chmod 2750 "$AGENT_HOME/bin"
```

### 3.5 환경 변수와 키 파일

컨테이너의 root 셸에서 로그인 프로필을 만들고 현재 셸에도 적용한다.

```sh
cat > /etc/profile.d/agent-app.sh <<'PROFILE'
export AGENT_HOME=/home/agent-admin/agent-app
export AGENT_PORT=15034
export AGENT_UPLOAD_DIR=$AGENT_HOME/upload_files
export AGENT_KEY_PATH=$AGENT_HOME/api_keys/t_secret.key
export AGENT_LOG_DIR=/var/log/agent-app
PROFILE
. /etc/profile.d/agent-app.sh
```

```sh
printf 'agent_api_key_test\n' > "$AGENT_HOME/api_keys/t_secret.key"
chown agent-admin:agent-core "$AGENT_HOME/api_keys/t_secret.key"
chmod 660 "$AGENT_HOME/api_keys/t_secret.key"
ln -s t_secret.key "$AGENT_HOME/api_keys/secret.key"
```

### 3.6 앱 실행

제공 압축 파일에서 arm64 실행 파일을 꺼내 `$AGENT_HOME/agent-app-linux-arm64`에 배치하고 소유자·그룹을 `agent-admin:agent-core`, 권한을 `750`으로 설정했다. 일반 계정 `agent-admin`으로 백그라운드 실행한다.

```sh
su - agent-admin -c 'umask 027; cd "$AGENT_HOME" && AGENT_KEY_PATH="${AGENT_KEY_PATH%/t_secret.key}" nohup setsid ./agent-app-linux-arm64 > "$AGENT_HOME/app.out" 2>&1 < /dev/null &'
```

앱 출력 파일은 `agent-core` 그룹에서 읽을 수 있도록 아래 권한을 적용했다.

```sh
chown agent-admin:agent-core "$AGENT_HOME/app.out"
chmod 640 "$AGENT_HOME/app.out"
```

### 3.7 monitor.sh와 cron

```sh
# 일반 계정이 방화벽 상태 조회만 할 수 있도록 허용한다.
echo 'agent-admin,agent-dev ALL=(root) NOPASSWD: /usr/sbin/ufw status' > /etc/sudoers.d/agent-monitor
chmod 440 /etc/sudoers.d/agent-monitor
```

Mac의 저장소 루트에서 `./scripts/install-b4-1.sh`를 실행한다. 이 명령은 세 Bash 스크립트를 설치하고 매분 모니터링과 매일 로그 보존 작업을 `agent-admin`의 기존 crontab에 추가한다. 등록 결과는 4.8에서 확인할 수 있다.

### 3.8 미션 문서와 다르게 적용한 사항

| 항목 | 미션 문서 | 실제 적용 | 이유 |
|---|---|---|---|
| `AGENT_KEY_PATH` | `$AGENT_HOME/api_keys/t_secret.key` | 로그인 셸은 명세의 파일 경로, 앱 기동 명령만 `$AGENT_HOME/api_keys` | 문서 값으로 실행하면 앱이 `Key Path Mismatch. Expected: .../api_keys`로 Boot에 실패한다. |
| 키 파일 이름 | `t_secret.key` | `t_secret.key` 유지, `secret.key` 심볼릭 링크 추가 | 앱이 `secret.key`를 찾는다. 문서가 요구한 파일도 그대로 유지했다. |
| 점검 프로세스 이름 | `agent_app.py` 또는 제공 앱 파일명 | `agent-app-linux` | 제공 앱은 실행 파일이고, 이 실습에서 `pgrep -x`가 보는 프로세스 이름(comm)은 15바이트로 잘린다. |

## 4. 필수 증거 자료

### 4.1 SSH 포트 변경과 Root 원격 접속 차단

> **체크리스트 1-1** · 유효 설정, 수신 포트, 일반 계정과 root의 SSH 접속 결과를 확인한다.
>
> **체크리스트 3-1** · 포트 변경은 기본 22번만 노리는 자동 접속을 줄인다. 새 포트를 알아내더라도 `PermitRootLogin no`가 root 직접 로그인을 막는다.

```text
$ grep -nE '^(Port|PermitRootLogin)[[:space:]]' /etc/ssh/sshd_config
14:Port 20022
33:PermitRootLogin no
$ sshd -T | grep -E '^(port|permitrootlogin) '
port 20022
permitrootlogin no
$ ss -tulnp | grep sshd
tcp   LISTEN 0      128          0.0.0.0:20022      0.0.0.0:*    users:(("sshd",pid=15,fd=3))
tcp   LISTEN 0      128             [::]:20022         [::]:*    users:(("sshd",pid=15,fd=4))
```

같은 공개키를 두 계정에 임시 등록해 호스트에서 접속을 시도한 결과다. 시험 후 키는 삭제했다.

```text
$ ssh -p 20022 agent-admin@127.0.0.1 id -un
agent-admin
$ ssh -p 20022 root@127.0.0.1 id -un
root@127.0.0.1: Permission denied (publickey,password).
```

### 4.2 방화벽 활성화와 허용 포트

> **체크리스트 1-2** · UFW의 활성 상태와 기본 수신 차단 정책을 보고 IPv4·IPv6에서 허용한 포트를 확인한다.

```text
$ ufw status verbose
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), deny (routed)
New profiles: skip

To                         Action      From
--                         ------      ----
20022/tcp                  ALLOW IN    Anywhere                  
15034/tcp                  ALLOW IN    Anywhere                  
20022/tcp (v6)             ALLOW IN    Anywhere (v6)             
15034/tcp (v6)             ALLOW IN    Anywhere (v6)             

```

별도 컨테이너에서 접속을 시도한 결과다. 18080은 차단 여부를 확인하려고 임시로 연 포트이며 시험 후 종료했다.

```text
20022/tcp: OPEN
15034/tcp: OPEN
18080/tcp: BLOCKED
```

### 4.6 monitor.sh 실행 결과

> **체크리스트 2-3** · `agent-dev:agent-core 750`으로 설치한다. 소유자 `agent-dev`가 수정하고, 그룹원 `agent-admin`은 자신의 crontab에서 읽고 실행한다. [설치와 cron 등록](../scripts/install-b4-1.sh)
>
> **체크리스트 4-1** · 웹 서버로 바꾸면 프로세스 이름, 실제 수신 포트, 점검 로그 경로를 지정하고 평소 사용량에 맞춰 임계값을 조정한다. [Nginx 적용 예](../docs/4-monitor.md#응용-질문)

```text
--- 앱 재시작 후
[HEALTH CHECK]
Checking process 'agent-app-linux'... [OK] (PID: 969)
Checking port 15034... [OK]
exit code: 0
```

경고 항목은 메시지만 출력하고 종료 코드 0으로 끝난다. MEM과 DISK는 임계값을 0으로 낮춘 임시 사본으로 경고 분기를 시험했다.

> **체크리스트 3-3** · 방화벽 비활성과 부하 상승 시에도 자원 측정과 로그 기록을 계속해야 장애 원인을 추적할 수 있다.

```text
# 경고 시험
--- 방화벽 비활성
[WARNING] Firewall is not active
exit code: 0
--- CPU 부하(실제 임계값 20%)
[WARNING] CPU threshold exceeded (100.0% > 20%)
exit code: 0
--- MEM, DISK(임시 사본, 임계값 0)
[WARNING] MEM threshold exceeded (5.1% > 0%)
[WARNING] DISK threshold exceeded (3% > 0%)
exit code: 0
--- 방화벽 복구: Status: active
```

추가로 자동 점검에서는 원래 임계값을 유지하고 `/proc/meminfo`와 `df`의 측정 입력만 고정했다. MEM 10%와 DISK 80%에서는 경고가 없었고, 10.1%와 81%에서는 각각 경고가 출력됐다. 두 실행 모두 종료 코드가 0이었고 초과 수치가 로그에 남았다.

### 4.7 monitor.log 누적 기록

> **체크리스트 1-6** · 시각·PID·CPU·MEM·DISK_USED가 같은 순서로 기록된 여러 줄을 확인한다.
>
> **체크리스트 2-2** · CPU는 1초간의 누적 시간 차이, MEM은 전체·가용 메모리, DISK는 `df -P /`의 사용률을 쓴다. 필드 순서를 고정해 시간 구간별 집계가 가능하다. [수집 코드](monitor.sh) · [집계 코드](../bonus/report.sh)

### 4.9 로그 용량 관리(10MB/10개)

> **체크리스트 1-8** · 교체 후 파일 수와 백업 내용을 대조해 현재 로그 1개와 백업 9개가 남았는지 확인한다.
>
> **체크리스트 2-4** · `monitor.sh`의 `rotate_log()`가 새 줄을 쓰기 전에 10 MiB 초과 여부를 검사한다. 초과하면 가장 오래된 백업을 지우고 기존 로그를 `.1`로 옮긴다.
>
> **체크리스트 4-3** · 단기에는 `df`와 `du`로 급증한 파일을 찾아 오래된 로그부터 공간을 확보한다. 중기에는 반복 오류를 고치고 교체·보관 기준과 디스크 경보를 정한다. [로그 급증 대응](../docs/4-monitor.md#응용-질문)
